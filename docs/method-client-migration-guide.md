# Migration guide: REST clients → CK method clients (skeleton)

> **Status: AB#8423 (F5.5 AB#5703) skeleton; identity wave 1 filled in by AB#8416.** Each migration wave fills in its own
> section. The method clients themselves are described in [method-clients.md](method-clients.md).

Phase 5 of CK v2 moves operations of `IIdentityServicesClient`, `ICommunicationServicesClient` and
`IAssetServicesClient` from REST endpoints to CK methods. For every migrated operation the REST method stays for its
REST window (one release train, at least three months from the GA of the method) and is marked `[Obsolete]` with a
pointer to its replacement. Consumers with warnings-as-errors see the obsolete warning from that release on.

## How to switch (general pattern)

1. Import the CK model that declares the method into the project that runs the source generator
   (`construction-kits.yaml`, e.g. `System.Identity-[3.2,4.0)`), so the generator emits the method client next to the DTOs.
   The SDK itself ships no generated client of a platform model: the consumer generates it from the model range it
   supports, so an SDK release never pins a model version.
2. Create the client over the tenant client you already use:
   `var users = new RtUserMethodClient(tenantClient);` (the tenant of `TenantClientOptions.TenantId`).
3. Replace the REST call with the method call; pass an idempotency key for calls you may retry, and reuse the same
   key for every retry of the same operation.
4. Replace exception-based handling of domain errors by the result: `if (!result.IsSuccess) { … result.Error.Code … }`
   with the constants of `{Method}Errors`. Authorization and validation errors still throw (`CkMethodCallException`,
   derived from `QlQueryErrorException`).

### Before / after

```csharp
// Before: REST
await identityServicesClient.ResetPassword(userName, newPassword);

// After: CK method client (generated by the consumer from System.Identity-[3.2,4.0))
var users = new RtUserMethodClient(tenantClient);
// One key per logical operation: create it once and pass the same key when you retry after a lost answer,
// so the service returns the first result instead of running the method again.
var idempotencyKey = Guid.NewGuid().ToString("N");
var result = await users.ResetPasswordAsync(userRtId, newPassword, idempotencyKey: idempotencyKey);
if (!result.IsSuccess)
{
    throw new InvalidOperationException($"Password reset refused: {result.Error!.Code}");
}
```

Differences to keep in mind:

- Methods address entities by **runtime id** (`rtId`), not by name. Look the entity up first where the REST call took a
  name.
- Errors are the declared codes of the CK model plus the platform `METHOD_*` codes; HTTP status codes are gone.
- A successful call carries an invocation id (`result.InvocationId`) for correlation with the handler log; a declared
  error carries its code and parameters instead (`result.Error`), and its `InvocationId` is `null`.

## Per-wave sections

### Identity wave 1 (AB#8416)

Since this release the REST role methods of `IIdentityServicesClient` are `[Obsolete]` (a warning, not an error):
`AddRoleToUser` and `RemoveRoleFromUser`. They keep calling REST during their REST window — the REST endpoints are
facades over the same handlers. A consumer with warnings-as-errors sees `CS0618` and switches (octo-cli: AB#8417,
octo-mcp-service: AB#8440).

`CreateUser` and `ResetPassword` are `[Obsolete]` (a warning, not an error) since AB#8860, pointing at
`RtUserMethodClient.CreateUserAsync` / `ResetPasswordAsync`. They became obsolete after the first-party consumers
switched (octo-cli #83, octo-mcp-service #74, AB#8418), so the SDK release does not turn their warnings-as-errors builds
red. Like the role methods, they keep calling REST (`POST users`, `POST users/ResetPassword`) during their REST window;
the identity service announces the deprecation of those endpoints with `Deprecation`/`Sunset` headers of their own wave
(octo-identity-services, AB#8860). No other user method of the SDK is obsolete; `SetRoles`, `Merge`, `ChangePassword`
and `SetPassword` had no SDK REST method and are new for SDK consumers.

#### Before you switch: password methods need the bus exposure

`CreateUser`, `ResetPassword`, `ChangePassword` and `SetPassword` carry a password. The identity service offers their
handlers on the method bus only when `Methods:Identity:EnablePasswordMethods` is on (default **off**; kept off on
staging-1, prod-1 and prod-2 until the restricted broker user, B0, is rolled out — octo-identity-services
`docs/configuration.md`). While it is off, the generated calls throw `CkMethodCallException` with
`METHOD_HANDLER_NOT_AVAILABLE`, but the REST calls work. So:

- Switch `CreateUser` and `ResetPassword` for clusters where the exposure is on. A consumer that must still reach a
  cluster where it is off keeps the REST call there and suppresses the warning at that call only
  (`#pragma warning disable CS0618` … `restore`), not project-wide, so the remaining call stays visible.
- `AddRole`, `RemoveRole`, `SetRoles` and `Merge` carry no password and are not gated.

#### Differences to the REST calls

- `CreateUserAsync` has no `ResetPasswordOnLogin` parameter; the handler creates the user with the flag `false`. The REST
  `CreateUser` sets the flag after creation when `UserDto.ResetPasswordOnLogin` is `true` (a REST-only flag). A caller
  that needs the forced password change keeps the REST `CreateUser` for that case.
- Roles are addressed by **name** (`AddRoleAsync(rtId, "Reader")`), the REST methods took the role id.
- Users are addressed by runtime id (below), the REST methods took the user name or e-mail address.

#### 1. Generate the client

```yaml
# construction-kits.yaml of the project that runs Meshmakers.Octo.Sdk.SourceGeneration
"$schema": "https://schemas.meshmakers.cloud/construction-kit-meta.schema.json"
imports:
  - System.Identity-[3.2,4.0)
```

The generator emits `RtUserMethodClient` (and the DTOs of System.Identity) in
`{RootNamespace}.DataTransferObjects.System.Identity.v3`. System.Identity 3.2.0 is the first version with all User
methods of this wave; the range keeps the project on the newest 3.x the catalog has.

```csharp
var users = new RtUserMethodClient(tenantClient); // ITenantClient of the tenant that owns the users
```

The methods address a user by its runtime id. Where the REST call took a user name or e-mail address, look the user
up first: `IIdentityServicesClient.GetUserByNameEmailOrId` returns it in `UserDto.UserId` (the user's runtime id), or
query it with the generated user DTOs.

#### 2. Create a user

```csharp
// Before
await identityServicesClient.CreateUser(new UserDto { Name = "alice", Email = "alice@example.com", Password = initial });

// After
var created = await users.CreateUserAsync("alice", email: "alice@example.com", password: initial,
    idempotencyKey: operationKey);
if (created.IsError(RtUserMethodClient.CreateUserErrors.PasswordPolicyViolation))
{
    // Declared error: a typed result, not an exception. Code, message and parameters come from the server's
    // password policy; the client keeps no copy of the policy.
    Console.Error.WriteLine($"{created.Error!.Code}: {created.Error.Message}");
    return;
}
if (!created.IsSuccess)
{
    // Any other declared error, e.g. RtUserMethodClient.CreateUserErrors.UserAlreadyExists (name or e-mail taken)
    throw new InvalidOperationException($"User not created: {created.Error!.Code}");
}
var aliceRtId = created.Value!; // rtId of the new user (read only after success)
```

The REST `CreateUser` reported the same refusal as an HTTP 400 (`ServiceClientException`) that the caller had to parse;
the method returns it as `created.Error` with `Code == "PASSWORD_POLICY_VIOLATION"`, the policy's message and
parameters, and `created.IsSuccess == false`. Platform errors (`METHOD_FORBIDDEN`, `METHOD_VALIDATION_FAILED`,
`METHOD_HANDLER_NOT_AVAILABLE`) still throw `CkMethodCallException` (table below).

#### 3. Reset a password (administrator)

```csharp
// Before
await identityServicesClient.ResetPassword("alice", newPassword);

// After
var alice = await identityServicesClient.GetUserByNameEmailOrId("alice"); // the method takes the rtId
var reset = await users.ResetPasswordAsync(alice.UserId!, newPassword, idempotencyKey: operationKey);
if (reset.IsError(RtUserMethodClient.ResetPasswordErrors.PasswordPolicyViolation))
{
    Console.Error.WriteLine($"{reset.Error!.Code}: {reset.Error.Message}"); // typed result, no exception
}
```

#### 4. Add and remove a role

```csharp
// Before (role id)
await identityServicesClient.AddRoleToUser("alice", roleId);
await identityServicesClient.RemoveRoleFromUser("alice", roleId);

// After (role name)
var added = await users.AddRoleAsync(aliceRtId, "Reader");
var removed = await users.RemoveRoleAsync(aliceRtId, "Reader");
// added.IsError(RtUserMethodClient.AddRoleErrors.RoleAlreadyAssigned), removed.IsError(...RemoveRoleErrors.RoleNotAssigned)

// New: replace all direct roles at once
var set = await users.SetRolesAsync(aliceRtId, ["Reader", "Editor"]);
```

#### 5. Merge users and own-password operations (new for SDK consumers)

```csharp
var merged = await users.MergeAsync(targetRtId, sourceUserName: "alice-old"); // source is deleted
var changed = await users.ChangePasswordAsync(myRtId, currentPassword, newPassword); // signed-in user
var set = await users.SetPasswordAsync(myRtId, newPassword); // signed-in user with external logins only
```

#### Error mapping

REST answered domain failures with an HTTP status (`ServiceClientException`); the method answers a declared code as a
result and throws only for platform errors.

| Operation | Declared codes (`{Method}Errors`) | Thrown (`CkMethodCallException.Code`) |
|-----------|-----------------------------------|---------------------------------------|
| `CreateUserAsync` | `USER_NAME_RESERVED`, `USER_ALREADY_EXISTS`, `PASSWORD_POLICY_VIOLATION` | `METHOD_FORBIDDEN` (no `UserManagement` role), `METHOD_VALIDATION_FAILED` |
| `ResetPasswordAsync` | `PASSWORD_POLICY_VIOLATION`, `SHADOW_USER_PASSWORD_NOT_ALLOWED` | `METHOD_FORBIDDEN`, `METHOD_TARGET_NOT_FOUND` (unknown `rtId`) |
| `AddRoleAsync` | `ROLE_NOT_FOUND`, `ROLE_ALREADY_ASSIGNED` | `METHOD_FORBIDDEN`, `METHOD_TARGET_NOT_FOUND` |
| `RemoveRoleAsync` | `ROLE_NOT_FOUND`, `ROLE_NOT_ASSIGNED` | `METHOD_FORBIDDEN`, `METHOD_TARGET_NOT_FOUND` |
| `SetRolesAsync` | `ROLE_NOT_FOUND` | `METHOD_FORBIDDEN`, `METHOD_TARGET_NOT_FOUND` |
| `MergeAsync` | `SOURCE_USER_NOT_FOUND`, `CANNOT_MERGE_INTO_ITSELF`, `MERGE_FAILED` | `METHOD_FORBIDDEN`, `METHOD_TARGET_NOT_FOUND` |
| `ChangePasswordAsync` | `PASSWORD_POLICY_VIOLATION`, `CURRENT_PASSWORD_INVALID`, `USER_LOCKED_OUT`, `SHADOW_USER_PASSWORD_NOT_ALLOWED` | `METHOD_FORBIDDEN` (not the caller's own user) |
| `SetPasswordAsync` | `PASSWORD_POLICY_VIOLATION`, `PASSWORD_ALREADY_SET`, `SHADOW_USER_PASSWORD_NOT_ALLOWED` | `METHOD_FORBIDDEN` (not the caller's own user) |

The clients, documents and error handling of this wave are proven in octo-sdk by `UserMethodClientTests`
(System.Identity 3.2.0 as generator input, documents validated against the recorded schema of an asset repository
tenant with System.Identity, recorded answers of the method gateway).

octo-cli switches its role commands (names unchanged) under AB#8417, octo-mcp-service its role tools under AB#8440;
both switched `CreateUser` and `ResetPassword` under AB#8418 (octo-cli #83, octo-mcp-service #74); the SDK marked the two
REST methods obsolete afterwards (AB#8860).
