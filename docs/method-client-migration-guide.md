# Migration guide: REST clients → CK method clients (skeleton)

> **Status: skeleton; identity wave 1, identity wave 2 and communication wave 3 are filled in.** Each
> migration wave fills in its own section. The method clients themselves are described in [method-clients.md](method-clients.md).

Phase 5 of CK v2 moves operations of `IIdentityServicesClient`, `ICommunicationServicesClient` and
`IAssetServicesClient` from REST endpoints to CK methods. For every migrated operation the REST method stays for its
REST window (one release train, at least three months from the GA of the method) and is marked `[Obsolete]` with a
pointer to its replacement. Consumers with warnings-as-errors see the obsolete warning from that release on.

## How to switch (general pattern)

1. Import the CK model that declares the method into the project that runs the source generator
   (`construction-kits.yaml`, e.g. `System.Identity-[3.2,4.0)`), so the generator emits the method client next to the DTOs.
   The SDK itself ships no generated client of a platform model: the consumer generates it from the model range it
   supports, so an SDK release never pins a model version.
2. Create the client over the tenant client you already use:
   `var users = new RtUserMethodClient(tenantClient);` (the tenant of `TenantClientOptions.TenantId`).
3. Replace the REST call with the method call; pass an idempotency key for calls you may retry, and reuse the same
   key for every retry of the same operation.
4. Replace exception-based handling of domain errors by the result: `if (!result.IsSuccess) { … result.Error.Code … }`
   with the constants of `{Method}Errors`. Authorization and validation errors still throw (`CkMethodCallException`,
   derived from `QlQueryErrorException`).

### Before / after

```csharp
// Before: REST
await identityServicesClient.ResetPassword(userName, newPassword);

// After: CK method client (generated by the consumer from System.Identity-[3.2,4.0))
var users = new RtUserMethodClient(tenantClient);
// One key per logical operation: create it once and pass the same key when you retry after a lost answer,
// so the service returns the first result instead of running the method again.
var idempotencyKey = Guid.NewGuid().ToString("N");
var result = await users.ResetPasswordAsync(userRtId, newPassword, idempotencyKey: idempotencyKey);
if (!result.IsSuccess)
{
    throw new InvalidOperationException($"Password reset refused: {result.Error!.Code}");
}
```

Differences to keep in mind:

- Methods address entities by **runtime id** (`rtId`), not by name. Look the entity up first where the REST call took a
  name.
- Errors are the declared codes of the CK model plus the platform `METHOD_*` codes; HTTP status codes are gone.
- A successful call carries an invocation id (`result.InvocationId`) for correlation with the handler log; a declared
  error carries its code and parameters instead (`result.Error`), and its `InvocationId` is `null`.

## Per-wave sections

### Identity wave 1

Since this release the REST role methods of `IIdentityServicesClient` are `[Obsolete]` (a warning, not an error):
`AddRoleToUser` and `RemoveRoleFromUser`. They keep calling REST during their REST window — the REST endpoints are
facades over the same handlers. A consumer with warnings-as-errors sees `CS0618` and switches (octo-cli and octo-mcp-service did).

`CreateUser` and `ResetPassword` are `[Obsolete]` (a warning, not an error) since the second identity release, pointing at
`RtUserMethodClient.CreateUserAsync` / `ResetPasswordAsync`. They became obsolete after the first-party consumers
switched (octo-cli #83, octo-mcp-service #74), so the SDK release does not turn their warnings-as-errors builds
red. Like the role methods, they keep calling REST (`POST users`, `POST users/ResetPassword`) during their REST window.
These two REST endpoints send no `Deprecation`/`Sunset` headers yet; their own deprecation wave in octo-identity-services
is a separate step. No other user method of the SDK is obsolete; `SetRoles`, `Merge`, `ChangePassword`
and `SetPassword` had no SDK REST method and are new for SDK consumers.

#### Before you switch: password methods need the bus exposure

`CreateUser`, `ResetPassword`, `ChangePassword` and `SetPassword` carry a password. The identity service offers their
handlers on the method bus only when `Methods:Identity:EnablePasswordMethods` is on (default **off**; kept off on
staging-1, prod-1 and prod-2 until the restricted broker user, B0, is rolled out — `octo-identity-services/docs/configuration.md`). While it is off, the generated calls throw `CkMethodCallException` with
`METHOD_HANDLER_NOT_AVAILABLE`, but the REST calls work. So:

- Switch `CreateUser` and `ResetPassword` for clusters where the exposure is on. A consumer that must still reach a
  cluster where it is off keeps the REST call there and suppresses the warning at that call only
  (`#pragma warning disable CS0618` … `restore`), not project-wide, so the remaining call stays visible.
- `AddRole`, `RemoveRole`, `SetRoles` and `Merge` carry no password and are not gated.

#### Differences to the REST calls

- `CreateUserAsync` has no `ResetPasswordOnLogin` parameter; the handler creates the user with the flag `false`. The REST
  `CreateUser` sets the flag after creation when `UserDto.ResetPasswordOnLogin` is `true` (a REST-only flag). A caller
  that needs the forced password change keeps the REST `CreateUser` for that case.
- Roles are addressed by **name** (`AddRoleAsync(rtId, "Reader")`), the REST methods took the role id.
- Users are addressed by runtime id (below), the REST methods took the user name or e-mail address.

#### 1. Generate the client

```yaml
# construction-kits.yaml of the project that runs Meshmakers.Octo.Sdk.SourceGeneration
"$schema": "https://schemas.meshmakers.cloud/construction-kit-meta.schema.json"
imports:
  - System.Identity-[3.2,4.0)
```

The generator emits `RtUserMethodClient` (and the DTOs of System.Identity) in
`{RootNamespace}.DataTransferObjects.System.Identity.v3`. System.Identity 3.2.0 is the first version with all User
methods of this wave; the range keeps the project on the newest 3.x the catalog has.

```csharp
var users = new RtUserMethodClient(tenantClient); // ITenantClient of the tenant that owns the users
```

The methods address a user by its runtime id. Where the REST call took a user name or e-mail address, look the user
up first: `IIdentityServicesClient.GetUserByNameEmailOrId` returns it in `UserDto.UserId` (the user's runtime id), or
query it with the generated user DTOs.

#### 2. Create a user

```csharp
// Before
await identityServicesClient.CreateUser(new UserDto { Name = "alice", Email = "alice@example.com", Password = initial });

// After
var created = await users.CreateUserAsync("alice", email: "alice@example.com", password: initial,
    idempotencyKey: operationKey);
if (created.IsError(RtUserMethodClient.CreateUserErrors.PasswordPolicyViolation))
{
    // Declared error: a typed result, not an exception. Code, message and parameters come from the server's
    // password policy; the client keeps no copy of the policy.
    Console.Error.WriteLine($"{created.Error!.Code}: {created.Error.Message}");
    return;
}
if (!created.IsSuccess)
{
    // Any other declared error, e.g. RtUserMethodClient.CreateUserErrors.UserAlreadyExists (name or e-mail taken)
    throw new InvalidOperationException($"User not created: {created.Error!.Code}");
}
var aliceRtId = created.Value!; // rtId of the new user (read only after success)
```

The REST `CreateUser` reported the same refusal as an HTTP 400 (`ServiceClientException`) that the caller had to parse;
the method returns it as `created.Error` with `Code == "PASSWORD_POLICY_VIOLATION"`, the policy's message and
parameters, and `created.IsSuccess == false`. Platform errors (`METHOD_FORBIDDEN`, `METHOD_VALIDATION_FAILED`,
`METHOD_HANDLER_NOT_AVAILABLE`) still throw `CkMethodCallException` (table below).

#### 3. Reset a password (administrator)

```csharp
// Before
await identityServicesClient.ResetPassword("alice", newPassword);

// After
var alice = await identityServicesClient.GetUserByNameEmailOrId("alice"); // the method takes the rtId
var reset = await users.ResetPasswordAsync(alice.UserId!, newPassword, idempotencyKey: operationKey);
if (reset.IsError(RtUserMethodClient.ResetPasswordErrors.PasswordPolicyViolation))
{
    Console.Error.WriteLine($"{reset.Error!.Code}: {reset.Error.Message}"); // typed result, no exception
}
```

The method has other side effects than REST `ResetPassword` (`octo-identity-services/docs/identity-methods.md`, "REST difference"):

| | REST `POST users/ResetPassword` | `User.ResetPassword-1` |
|---|---|---|
| Lockout of the user | stays | lifted (lockout end and failed-access count reset) |
| E-mail | a second reset token is e-mailed to the user | no e-mail (a notification is planned) |

A caller that relied on the lockout staying, or on the e-mail, keeps that in mind when it switches.

#### 4. Add and remove a role

```csharp
// Before (role id)
await identityServicesClient.AddRoleToUser("alice", roleId);
await identityServicesClient.RemoveRoleFromUser("alice", roleId);

// After (role name)
var added = await users.AddRoleAsync(aliceRtId, "Reader");
var removed = await users.RemoveRoleAsync(aliceRtId, "Reader");
// added.IsError(RtUserMethodClient.AddRoleErrors.RoleAlreadyAssigned), removed.IsError(...RemoveRoleErrors.RoleNotAssigned)

// New: replace all direct roles at once
var set = await users.SetRolesAsync(aliceRtId, ["Reader", "Editor"]);
```

#### 5. Merge users and own-password operations (new for SDK consumers)

```csharp
var merged = await users.MergeAsync(targetRtId, sourceUserName: "alice-old"); // source is deleted
var changed = await users.ChangePasswordAsync(myRtId, currentPassword, newPassword); // signed-in user
var set = await users.SetPasswordAsync(myRtId, newPassword); // signed-in user with external logins only
```

#### Error mapping

REST answered domain failures with an HTTP status (`ServiceClientException`); the method answers a declared code as a
result and throws only for platform errors.

| Operation | Declared codes (`{Method}Errors`) | Thrown (`CkMethodCallException.Code`) |
|-----------|-----------------------------------|---------------------------------------|
| `CreateUserAsync` | `USER_NAME_RESERVED`, `USER_ALREADY_EXISTS`, `PASSWORD_POLICY_VIOLATION` | `METHOD_FORBIDDEN` (no `UserManagement` role), `METHOD_VALIDATION_FAILED` |
| `ResetPasswordAsync` | `PASSWORD_POLICY_VIOLATION`, `SHADOW_USER_PASSWORD_NOT_ALLOWED` | `METHOD_FORBIDDEN`, `METHOD_TARGET_NOT_FOUND` (unknown `rtId`) |
| `AddRoleAsync` | `ROLE_NOT_FOUND`, `ROLE_ALREADY_ASSIGNED` | `METHOD_FORBIDDEN`, `METHOD_TARGET_NOT_FOUND` |
| `RemoveRoleAsync` | `ROLE_NOT_FOUND`, `ROLE_NOT_ASSIGNED` | `METHOD_FORBIDDEN`, `METHOD_TARGET_NOT_FOUND` |
| `SetRolesAsync` | `ROLE_NOT_FOUND` | `METHOD_FORBIDDEN`, `METHOD_TARGET_NOT_FOUND` |
| `MergeAsync` | `SOURCE_USER_NOT_FOUND`, `CANNOT_MERGE_INTO_ITSELF`, `MERGE_FAILED` | `METHOD_FORBIDDEN`, `METHOD_TARGET_NOT_FOUND` |
| `ChangePasswordAsync` | `PASSWORD_POLICY_VIOLATION`, `CURRENT_PASSWORD_INVALID`, `USER_LOCKED_OUT`, `SHADOW_USER_PASSWORD_NOT_ALLOWED` | `METHOD_FORBIDDEN` (not the caller's own user) |
| `SetPasswordAsync` | `PASSWORD_POLICY_VIOLATION`, `PASSWORD_ALREADY_SET`, `SHADOW_USER_PASSWORD_NOT_ALLOWED` | `METHOD_FORBIDDEN` (not the caller's own user) |

The clients, documents and error handling of this wave are proven in octo-sdk by `UserMethodClientTests`
(System.Identity 3.2.0 as generator input, documents validated against the recorded schema of an asset repository
tenant with System.Identity, recorded answers of the method gateway).

octo-cli switches its role commands (names unchanged) and octo-mcp-service its role tools;
both switched `CreateUser` and `ResetPassword` (octo-cli #83, octo-mcp-service #74); the SDK marked the two
REST methods obsolete afterwards.

### Identity wave 2

Feature F5.2 turned the remaining REST writes of identity administration into facades over CK methods of
`System.Identity` (3.3.0 - 3.8.0, `octo-identity-services/docs/identity-rest-facades.md`). The matching 57 methods of
`IIdentityServicesClient` keep calling REST during their REST window; the REST endpoints run the same handlers. They are
**not obsolete yet**: as with the user methods, they become `[Obsolete]` (a warning, not an error) only after the first-party
consumers switched (octo-cli and octo-mcp-service), so no warnings-as-errors build of ours turns
red. The reads (`Get*`, `LookupSourceUser`, the cross-tenant grant permissions) stay. Switch now, except for the
secret-carrying methods below where the gate is off; the table below is also the list of the future obsolete messages.

#### Before you switch: secret-carrying methods need the bus exposure

Eleven wave 2 methods carry a secret (a parameter or the result), and the identity service offers their handlers on the
method bus only when `Methods:Identity:EnablePasswordMethods` is on — the same gate as the password methods of wave 1
(default **off**; kept off on staging-1, prod-1 and prod-2 until the restricted broker user, B0, is rolled out —
`octo-identity-services/docs/configuration.md`). While it is off, the generated call throws `CkMethodCallException` with
`METHOD_HANDLER_NOT_AVAILABLE` — also when no secret is passed (e.g. `CreateClientAsync` without `clientSecret`) — but
the REST call works (the REST facades run the handlers in-process).

| Gated method (marked † in the table below) | Replaces |
|---|---|
| `RtClientMethodClient.CreateClientAsync`, `UpdateClientAsync` | `CreateClient`, `UpdateClient` |
| `RtClientMethodClient.AddSecretAsync`, `UpdateSecretAsync`, `RemoveSecretAsync` | `CreateApiSecretForClient`, `UpdateApiSecretClient`, `DeleteApiSecretClient` |
| `RtApiResourceMethodClient.AddSecretAsync`, `UpdateSecretAsync`, `RemoveSecretAsync` | `CreateApiSecretForApiResource`, `UpdateApiSecretApiResource`, `DeleteApiSecretApiResource` |
| `RtClientMethodClient.RotateMirrorSecretAsync` | — (no SDK REST method) |
| `Rt<Provider>IdentityProviderMethodClient.CreateIdentityProviderAsync`, `UpdateIdentityProviderAsync` | `CreateIdentityProvider`, `UpdateIdentityProvider` |

So switch these calls only for clusters where the exposure is on; a consumer that must still reach a cluster where it is
off keeps the REST call there (and, once the REST method is obsolete, suppresses the warning at that call only). All
other wave 2 methods carry no secret and are not gated.


#### Differences to the REST calls

- Entities are addressed by **runtime id**. Where the REST method took a name or a client id (roles, API scopes, API
  resources, clients, data permissions), look the `rtId` up first: `ClientDto.RtId`, `RoleDto.Id`, `GroupDto.Id`,
  `DataPermissionDto.Id`, `EmailDomainGroupRuleDto.RtId`, `IdentityProviderDto.RtId`, or a query with the generated
  DTOs (API scopes and API resources).
- Roles are named, not referenced by id (`SetRolesAsync`, `AddRoleAsync`, `CreateGroupAsync`).
- Domain failures are declared errors in the result (table below); REST answered them with an HTTP status or a problem
  body (`ServiceProblem`). Authorization (`METHOD_FORBIDDEN`), validation (`METHOD_VALIDATION_FAILED`) and an unknown target
  (`METHOD_TARGET_NOT_FOUND`) still throw `CkMethodCallException`; so does `METHOD_HANDLER_NOT_AVAILABLE` for a † method where the bus exposure is off (above).
- The facades changed a few REST answers on purpose (e.g. a `500` that was a bug became `404`); the methods behave like
  the facades. The full list per endpoint: `octo-identity-services/docs/identity-rest-facades.md`.
- Secrets: `AddSecretAsync` and `RotateMirrorSecretAsync` return the generated secret once; `clientSecret` and

### Communication wave 3

Feature F5.3 turned the 22 operation endpoints of the communication controller into facades over CK methods of
`System.Communication` (4.17.0 - 4.19.0; `octo-communication-controller-services/docs/rest-method-facades.md`, with the
parity table per endpoint). The matching methods of `ICommunicationServicesClient` keep calling REST during their REST
window; the REST endpoints run the same handlers. They are **not obsolete yet**: as with the user methods and identity wave 2, they become
`[Obsolete]` only after octo-cli and octo-mcp-service switched, so no warnings-as-errors build of ours turns
red. The reads (`Get*`), the tenant-level operations (`EnableAsync`, `DisableAsync`, `SetLifecycleAsync`),
`ReconfigureLogLevelAsync` and `SwitchServiceAccountsToImpersonationAsync` stay REST. The table below is also the list of
the future obsolete messages.

All methods require the role `CommunicationManagement` and the scope `octo_api`. The REST endpoints accept every
`octo_api` caller and run such a caller without the role on their guarded direct path; `Pipeline/execute` also accepts
the read-only scope there. The method refuses both callers with `METHOD_FORBIDDEN`, so check the role and scope of your
client before you switch `ExecutePipelineAsync`. No result carries a secret: `RotateServiceAccountSecretAsync` stores the
new secret in the adapter's configuration and never returns it. Two parameters are sensitive (the model marks them so; the
platform never echoes or logs them): `pipelineDefinition` of `RtPipelineMethodClient.DeployAsync` (a definition can carry
credentials) and `input` of `ExecuteAsync`. Keep them out of your own logs too.

#### 1. Generate the clients

```yaml
# construction-kits.yaml of the project that runs Meshmakers.Octo.Sdk.SourceGeneration
"$schema": "https://schemas.meshmakers.cloud/construction-kit-meta.schema.json"
imports:
  - System-[2.7,3.0)
  - System.Communication-[4.19,5.0)   # or the lowest version your calls need, see the table
```

Import `System` too: 16 communication types derive from `System/Configuration`, and their DTOs need the System DTOs
(older SDK versions could not compile the System.Communication DTOs at all). The generator emits one client per
concrete type with methods in `{RootNamespace}.DataTransferObjects.System.Communication.v4`: `RtAdapterMethodClient`,
`RtAdapterPoolMethodClient`, `RtApplicationMethodClient`, `RtPipelineMethodClient`, `RtDataFlowMethodClient`,
`RtDeploymentSiteMethodClient` and `RtPipelineTriggerMethodClient`. The abstract `DeployableWorkload` gets no client: its
methods (`Deploy`, `Undeploy`, `SetChartVersion`, `Wake`) are on the client of the workload's **concrete** type. The
target is looked up by that type, so an adapter pool's `rtId` sent through `RtApplicationMethodClient` throws
`METHOD_TARGET_NOT_FOUND`. Take the type from the workload you read (`WorkloadSummaryDto` of `GetWorkloadsByChartAsync`, or
the entity's `ckTypeId`).

#### 3. Examples

```csharp
// Before: REST, exceptions for every failure
await communicationServicesClient.DeployPipelineAsync(adapterRtId, pipelineRtId, definition);
var executionIdBefore = await communicationServicesClient.ExecutePipelineAsync(pipelineRtId, input);

// After: method clients, declared errors as results
var pipelines = new RtPipelineMethodClient(tenantClient);
var deployed = await pipelines.DeployAsync(pipelineRtId, adapterRtId, definition, idempotencyKey: operationKey);
if (deployed.IsError(RtPipelineMethodClient.DeployErrors.PipelineDeployRejected))
{
    // REST 422; reason: adapter-rejected, adapter-service (REST 404) or unexpected (REST 400)
    Console.Error.WriteLine($"{deployed.Error!.Parameters["reason"]}: {deployed.Error.Parameters["message"]}");
}

var started = await pipelines.ExecuteAsync(pipelineRtId, input, isDryRun: false);
if (!started.IsSuccess)
{
    // e.g. RtPipelineMethodClient.ExecuteErrors.PipelineExecutionStartFailed; Value is null then
    throw new InvalidOperationException($"Pipeline not started: {started.Error!.Code}");
}

var executionId = started.Value!.ExecutionId; // a string, as before; started.Value.StartedAt is new
```

```csharp
// Workload: the client of the concrete type
var pools = new RtAdapterPoolMethodClient(tenantClient);
var scaled = await pools.ScaleAsync(poolRtId, replicas: 3);
if (scaled.IsError(RtAdapterPoolMethodClient.ScaleErrors.CommunicationDisabled))
{
    // REST 409: enable Communication for the tenant first
}
```

#### Differences to the REST calls

- Entities are addressed by **runtime id**; a workload method needs the client of the workload's concrete type (above).
- Domain failures are declared errors in the result (table below); REST answered them with 400, 404, 409 or 422.
  Authorization (`METHOD_FORBIDDEN`), validation (`METHOD_VALIDATION_FAILED`, e.g. a negative `replicas`), an unknown target
  (`METHOD_TARGET_NOT_FOUND`) and a timeout (`METHOD_TIMEOUT`, REST 504) still throw `CkMethodCallException`.
- The role `CommunicationManagement` is required (REST: any `octo_api` caller, see above).
- Each method has a timeout (pipeline execute 30 s, workload deploy 90 s, site undeploy and trigger deploy 120 s, ...); REST
  had none before the facades.
- Every call writes one method audit event; a move of several pipelines is one call per pipeline.
